## 一、项目目标

1. **协议复刻**: 纯 Python 实现同花顺柜台交易协议（登录/查询/委托），不依赖客户端
2. **可分发**: pip 安装包（`ths-trade-client`），供量化框架/其他程序直接调用
3. **可维护**: 协议随客户端版本变化时，有标准化抓包→模板→验证的流程

- [ ] **1.3 撤单** —— 2026-10-19 深入探测, 命令号已锁定, 报文结构仍缺
  - ✅ 全部历史抓包中**从未出现 0222**(只有 0221/0321)
  - ⚠️ **重要修正**: 早先"0222/0322 被网关识别"的判断建立在**外层 wire 命令**上, 是错的。
    后续证明**外层命令被网关忽略, 业务由明文内部 cmd `[6:8]` 决定**:
    外层 0222 配内部 `0201` 会**执行买入**(回资金不足), 外层 0322 配内部 `0301` **执行卖出**。
    已知内部 cmd: `0x0201`=买, `0x0301`=卖(沪深通用, 市场走 `scdm` 字段)
  - ✅ 内部 `XX02` 族(`0102/0202/0302/0222/0322`)一律返回「功能的服务，敬请谅解！」,
    而 `0402`→「无效请求」、`0212`→「验证签名错」; 拒绝发生在**服务层**:
    用 8 种完全不同报文体(原委托体/加 htbh/ddhb/wtbh/cxbh/换 type=cxtd|ct/截短体/全零体/
    委托序号样式)打 `0202`, **返回完全一致** ⇒ 无法由应答反推报文字段, 纯黑盒探测到此为止
  - ✅ 委托明文尾部是 **k=v 文本**: `count=1 / client=exe / lxfs= / sell1price= /
    index=1 / cdr_type=0 / workid=5 / req_start_tickcount=… / clientver=… / xd_djpp=0 /
    zjzh=… / buy1price=6.02 / interact=1 / confirm=0 / solicited=0 / wtjg=8.500000 /
    kernelver=… / type=ptwt / plwt=0 / wtsl=100 / menuid=161 / scdm=2`; 前 0x00-0x132
    是二进制区(magic fdff + sess + 内部cmd + md5签名槽[8:24] + 资金账号/股东号/代码)
  - ✅ 模拟盘路线**不通**: 用**与 IV 无关**的方法验证(CBC 第2块起与IV无关, 穷举2字节 +
    raw-inflate 判定): sim_login/sim_cap/sim_trade 三个会话共 44 个 0x10 帧,
    **用实盘 KEY 无一能解** → 模拟盘用的是另一把 KEY, 抓了也解不开
  - ⚠️ **修正**: 此前"模拟盘标准启动序列返回『数据包无效：帐户无效』"的结论**不可信**。
    该文本在模拟盘抓包中根本不存在(原始/base64/zlib 三种形态都搜不到), 很可能来自
    xiadan-plus 通道或 HTTP 通道。**凡涉及模拟盘的业务级结论都应视为未验证**;
    唯一确证的是: 模拟盘交易通道的密钥材料与实盘不同
  - ✅ 二进制路线部分成功: `xiadan.exe` 里 `tjdd_chedan` 出现 616 次(命令注册表),
    但**委托报文不是静态模板**(用限价买模板 24 字节切片全盘搜索 0 命中) → 代码逐字段拼装
  - ✅ HTTP 通道只含**港股通** 11 个命令(ggt_cd/mairu/maichu/...), 无 A 股撤单;
    但其 URL 模板确认撤单核心参数是 **`htbh`(合同号/委托号)** + `ex_gdzh` + `ex_scdm` + `ex_zqdm`
  - ⬜ 拿到明文的唯一现实途径: 账户放一笔小钱(如 2000 元) → 挂**远离市价**的限价单
    (不会成交) → 撤单 → 抓包。约 15 分钟
  - ⬜ 备选: 反汇编 `xiadan.exe` 中 0222 的构造函数(工作量大)
  - 验收: API `cancel(order_id)` 实盘撤单成功

## 五、风险与依赖

| 风险 | 说明 | 对策 |
|---|---|---|
| 协议随版本失效 | 客户端升级可能改帧/字段/加密 | 抓包→模板流程标准化（tools 已就绪） |
| 账号资金 | 实盘验证需要资金（当前账户不足, 委托只能到资金检查） | 小额验证；资金检查即视为协议通过 |
| 合规 | 程序化交易需遵守券商/监管要求 | 仅自有账户；控制频率；保留人工确认 |
| 敏感数据 | 抓包含账号/股东号/密钥 | captures/ 已 .gitignore；文档不落真实密钥 |
| 深市/限价模板缺失 | 需要真客户端实际操作一次抓包 | 用户配合下单即可（已验证流程） |
| 卖出验证需持仓 | 卖出需账户持有股票才能真实验证 | 用有持仓股票小额卖出（顺便变现）；无持仓则以持仓检查拒绝为通过标准 |

## 六、如何继续抓包（操作手册）

```bash
# 【标准流程】抓委托/查询报文 (推荐: 全自动, 抓后即解密)
ths-capture-orders --timeout 600 --out captures/xxx
#   → 期间在真客户端做对应操作 (下单/查询/撤单)
#   → 抓帧即自动扫 xiadan 内存恢复会话IV, 结束后输出明文 dec_*_<cmd>.bin

# 【取配置】一次性提取账号配置+站点列表+设备信息
ths-capture-profile                                  # → local_profile.json

# 【分析】提炼模板 → 脱敏 → base64 内嵌 trade_msg.py _TPL
#    补丁函数: sess(0x02)/tick(0x88)/seq(0x8c)/md5槽(0x08) + 字段替换
#    验收: 重建明文 == 捕获明文 (逐字节) + 实盘业务级应答
```

**要点**: 告别帧必须抓到会话IV —— 抓包工具会在抓到首个柜台帧时**预扫内存**中的密钥描述符
(KEY特征码 + IV槽) 恢复IV, 因此**不需要重启/重连客户端**, 操作完即可关。

**模板化标准流程**: 真客户端操作 → 捕获内容 → 用会话IV解密 → 定位差异字段 →
作为模板内嵌（base64）→ 补丁函数（sess/tick/seq/md5）→ 实盘验证。
